# Профиль, знакомства и прочтение

## Профиль

`GET /api/profile` возвращает `{profile:{id,name,avatar_url?,age,bio,city}}`.
`PUT /api/profile` принимает `{name,age,bio,city}` и возвращает тот же конверт.
Имя обязательно, до 100 символов. Описание — до 100 Unicode-символов после
удаления крайних пробелов. Город необязателен, до 100 символов. Возраст — целое
неотрицательное число лет, без отдельного продуктового возрастного диапазона;
технический тип хранения PostgreSQL INTEGER. `null` означает незаполненное поле.

Регистрация и чаты работают без профиля. Знакомства требуют возраста и непустого
описания, что проверяет сервер. Для старых аккаунтов ничего не выдумывается.
Фото необязательно: существующая загрузка хранит нормализованное изображение
в PostgreSQL, а интерфейс без фото показывает инициалы. Файловая система Render
для постоянного хранения не используется.

## Знакомства

- `GET /api/discovery`: до 30 полных карточек. Исключены сам пользователь,
  неполные профили, уже поставленные лайки и состоявшиеся совпадения.
- `GET /api/discovery/likes`: до 30 входящих лайков без своего ответа/совпадения.
  Ответ содержит полную карточку для открытия подробностей без второго запроса.
- `POST /api/discovery/votes`: `{user_id,liked:true|false}`.
  Ответ: `{matched,conversation_id}`, пустой ID до совпадения.

Отклонённая карточка может вернуться через 7 дней. Это выбранное начальное правило.
Повтор одинакового ответа не сдвигает срок. Принятие входящего лайка — обычный
ответный лайк. На этапе MVP не добавлены платежи или дополнительные действия.

Взаимные лайки выполняются в одной транзакции. Блокировка пары пользователей
действует и до появления строки совпадения, поэтому встречные одновременные
запросы не дублируют данные. Уникальная пара диалога сохраняется; существующая
переписка используется повторно. Системное сообщение «Вы стали друзьями!»
создаётся один раз, `kind:"system"`, `sender_id:""` в JSON. Оно непрочитано
для обоих участников, пока каждый самостоятельно не просмотрит чат.

## Непрочитанное и галочки

Сервер хранит `conversation_members.last_read_id`, монотонную отметку просмотра.
Собственные текстовые/голосовые сообщения не увеличивают непрочитанное.
`conversations[].unread_count` — число непрочитанных в конкретном чате.
`GET /api/unread` возвращает `{unread_chats}` — число чатов с непрочитанным,
включая переписки за пределами загруженных страниц.

`GET /api/conversations/{id}/read` возвращает
`{unread_count,last_message_id,peer_last_read_id}` и ничего не отмечает.
`POST` по тому же адресу принимает `{last_message_id:"123"}` и возвращает
`{last_read_id:"123"}`. ID должен принадлежать этой переписке; чужой ID — 404.
Старый/повторный запрос не уменьшает курсор. Запись сообщений и отметки просмотра
сериализуются по диалогу, чтобы сообщение с меньшим ID не зафиксировалось после
более новой отметки просмотра. Права участника проверяются и при чтении состояния.

Клиент подтверждает просмотр после появления последнего сообщения в видимой
области, при открытом разделе чатов, активной вкладке и фокусе окна. Фоновая
загрузка истории ничего не отмечает. Одна галочка означает «Сохранено на сервере»,
две лаймовые — «Прочитано», на основании серверного курсора собеседника.
Подтверждения доставки на устройство нет.

До появления этой функции история просмотра не сохранялась, поэтому миграция
не выдумывает прочтение старых сообщений: они учитываются до первого просмотра.
Полноэкранный звонок также приостанавливает подтверждение просмотра чата.

## Pusher и нагрузка

Один WebSocket используется списком чатов, открытой перепиской и звонками.
В `private-user-<свой id>` публикуются:

| Событие | Данные | Когда |
|---|---|---|
| `conversation.updated` | `{conversation_id}` | Создание/получение диалога, совпадение |
| `conversation.message` | `{conversation_id}` | Сохранение текста/голоса, включая повтор |
| `conversation.read` | `{conversation_id,user_id,last_read_id}` | Подтверждение просмотра |
| `discovery.updated` | `{}` | Лайк/отклонение |

`message.created` в канале переписки и события звонков сохранены. Личный канал
слушается даже без выбранного чата. После подписки/восстановления выполняется
HTTP-синхронизация. События не заменяют PostgreSQL и могут дублироваться.
Обновление прочтения отправляется обоим пользователям и всем их устройствам.

При работающем Pusher постоянных GET `/calls` нет. HTTP нужен при входе,
восстановлении/возврате фокуса, событиях и действиях пользователя. Если подписка
не работает, резервная проверка звонков выполняется раз в 30 секунд, остальные
состояния — раз в 60 секунд в видимой вкладке. Скрытая вкладка без активного
звонка не опрашивает звонки. Проверка доступности медиа больше не запускает
бесконечный таймер при выключенной функции.

Публикация событий выполняется после фиксации данных. Гарантированной фоновой
очереди повторов пока нет. После пропущенного события состояние восстанавливают
повторная подписка, возврат фокуса, резервный запрос при сбое или ручное обновление.

## Проверка

`go test ./...` из `api`, с `TEST_DATABASE_URL` отдельной тестовой базы для
интеграционных проверок. Тесты используют реальные транзакции PostgreSQL,
проверяют встречные одновременные лайки, повторы, права доступа, системное
сообщение и сохранённые отметки прочтения. `npm test`, `npm run build`,
`npm run lint` из `client` проверяют интерфейсную логику и сборку.
