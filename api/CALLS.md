# Звонки один на один: серверная часть

Go управляет приглашениями, правами участников и обменом служебными данными.
Pusher сообщает о приглашении и новых сигналах. Звук/видео передаёт WebRTC в браузере.
Реализация камеры, микрофона и RTCPeerConnection находится на фронтенде.

Клиент начинает и принимает звонок с `getUserMedia({audio:true,video:false})`:
обязателен только микрофон. Камера включается отдельной кнопкой по желанию;
её отсутствие или запрет не прерывают аудиозвонок. При выключении камеры
видеодорожка останавливается, микрофон продолжает работать. Отдельный режим
в серверном API не требуется: существующий SDP-сигналинг поддерживает оба случая.

## Состояния

```text
ringing → accepted → ended
   ├──→ rejected (получатель)
   ├──→ cancelled (звонящий)
   └──→ expired (60 секунд без ответа)
accepted → expired (максимум 2 часа)
```

Звонок занимает обоих пользователей с момента приглашения. Другой звонок с любым
из занятых пользователей возвращает 409 participant_busy. Доступ постороннего — 404.
Повтор создания с тем же client_call_id возвращает прежний звонок. Повтор уже
успешного действия не меняет version. Клиент применяет call.updated только если
version не меньше уже известного значения; для строгой синхронизации запрашивает GET.

Сроки проверяются при обращениях к API. Отдельного фонового таймера нет: фронтенд
использует expires_at и при наступлении срока запрашивает состояние. Просроченное
приглашение нельзя принять. После перезапуска API состояние сохраняется в БД.
В этом MVP нет heartbeat: потерянное соединение само не завершает accepted до
двухчасового лимита. При выходе/ошибке/закрытии экрана фронтенд вызывает end/cancel.

## Маршруты

Все требуют cookie авторизации и разрешённый Origin. POST — application/json.

| Метод | Адрес | Тело/назначение |
|---|---|---|
| POST | /api/conversations/{id}/calls | {"client_call_id":"новый UUID"} |
| GET | /api/calls | Свои активные входящие/исходящие звонки |
| GET | /api/calls/{callID} | Состояние конкретного звонка |
| POST | /api/calls/{callID}/actions | {"action":"accept"}, reject, cancel или end |
| POST | /api/calls/{callID}/signals | client_signal_id, type, payload |
| GET | /api/calls/{callID}/signals?after=0 | Сигналы, адресованные текущему пользователю |

UUID создаются через crypto.randomUUID(). Сохраняйте ID при повторе HTTP-запроса.
Для сигналов after — последний обработанный ID; next_cursor возвращается строкой.
При has_more=true загрузите следующую страницу сразу. Не запускайте несколько
параллельных загрузок сигналов одного звонка; применяйте их последовательно.

## Pusher

После login подпишитесь на private-user-<свой ID> через тот же customHandler,
который описан в CHAT.md. GET /api/auth/me даёт свой ID.
Подписка на чужой личный канал запрещена.

- call.updated: {"call":{...}} в личные каналы обоих участников.
- call.signal: {"call_id":"...","signal_id":"...","type":"offer"} только получателю сигнала.

call.updated со status=ringing и callee_id=свой ID означает входящее приглашение.
После подключения к Pusher вызовите GET /api/calls: это восстановит приглашение,
если событие было пропущено. То же делайте при восстановлении соединения.
После отключения аккаунта завершите звонок, отключите Pusher и закройте RTCPeerConnection.

В ответах POST поле realtime: published/failed/disabled. Изменение состояния или
сигнал уже сохранены, даже если уведомление не доставлено. Для восстановления
используйте GET; автоматической фоновой очереди публикации пока нет.
Без ключей Pusher можно проверять HTTP-логику, но входящие события работать не будут.

## Порядок WebRTC на фронтенде

1. Подписаться на личный канал и проверить активные звонки.
2. Звонящий создаёт звонок; второй пользователь видит приглашение.
3. Получатель разрешает доступ к камере/микрофону и вызывает accept.
4. Звонящий после подтверждения accepted создаёт RTCPeerConnection, добавляет
   свои дорожки, делает createOffer/setLocalDescription и POST сигнала offer.
5. Получатель забирает сигналы через GET, делает setRemoteDescription(offer),
   добавляет свои дорожки, создаёт answer и отправляет его серверу.
6. Звонящий применяет answer через setRemoteDescription.
7. Оба передают ICE-кандидаты через POST сигналов; полученные применяют через
   addIceCandidate. Кандидаты до remoteDescription временно складываются в очередь.
8. При завершении: POST action=end, peerConnection.close(), остановить все
   дорожки getUserMedia через track.stop().

Пример offer:

```json
{
  "client_signal_id": "30000000-0000-0000-0000-000000000001",
  "type": "offer",
  "payload": {"type":"offer","sdp":"v=0\r\n..."}
}
```

answer аналогичен. ICE:

```json
{
  "client_signal_id": "30000000-0000-0000-0000-000000000002",
  "type": "ice",
  "payload": {"candidate":"candidate:...","sdpMid":"0","sdpMLineIndex":0}
}
```

Для конца кандидатов можно передать {"candidate":""}. Сигналы принимаются
только в accepted. offer может отправить только звонящий, answer — получатель.
API не разбирает SDP целиком и не гарантирует совместимость конкретных браузеров.
Запрос ограничен 64 КиБ, payload — 60 КиБ. В Pusher передаётся только ID, потому
что SDP может превышать лимит размера события. Сигналы удаляются при end и при
следующем обращении к API после expiry. Аудио/видео в PostgreSQL не сохраняются.

## Что ещё нужно для настоящего видеозвонка

- Приложение Channels и заполненные четыре PUSHER_* в .env.
- WebRTC-код на фронтенде и HTTPS при публикации (localhost подходит для разработки).
- STUN/TURN-конфигурация для RTCPeerConnection. TURN пока не развёрнут и не настроен:
  его нужно добавить отдельным шагом для звонков между разными сетями.
- Проверка двумя браузерами на реальных сетях. Тесты сервера не заменяют такую проверку.

Источники: [WebRTC](https://webrtc.org/getting-started/peer-connections),
[лимиты событий Pusher](https://pusher.com/docs/channels/server_api/http-api/).
